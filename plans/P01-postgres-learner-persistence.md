# P01 — PostgreSQL Learner Persistence Foundation

## Goal

Replace browser-carried signed learner state as the only system of record with a
PostgreSQL-backed, provider-neutral persistence boundary while preserving the
existing deterministic learning engine and deployed learner workflow.

## Implemented architecture

### Configuration and dependency boundary

- `AI_PLATFORM_PERSISTENCE_MODE` is explicitly `signed_state` or `postgres`.
- `signed_state` remains the rollback-compatible default and creates no database
  engine.
- `postgres` requires a secret `AI_PLATFORM_DATABASE_URL` using only
  `postgresql+psycopg://`.
- The locked runtime uses SQLAlchemy `2.0.51`, Alembic `1.18.5`, and Psycopg `3.3.4`.
- The lockfile was generated by `uv`; it was not edited manually.
- The async engine uses `NullPool`, bounded connect timeout, pre-ping, lazy
  connection creation, and explicit shutdown disposal. This avoids multiplying
  resident connection pools across serverless application instances.

### Versioned schema and migration

Alembic revision `20260724_01` creates:

- provider-neutral account records;
- account-owned learner aggregate snapshots;
- append-only learner events containing the exact accepted state version;
- account-scoped idempotency uniqueness;
- aggregate-version uniqueness; and
- transactional outbox records with one outbox record per event.

The migration has an explicit reverse-order downgrade. CI is configured to verify
empty-database upgrade and downgrade/upgrade round trips against PostgreSQL 18.

### Transaction and replay contract

`PostgresLearnerStateRepository` atomically:

1. resolves an existing idempotent command;
2. upserts the provider-neutral account;
3. inserts or optimistic-concurrency-updates the snapshot;
4. appends the versioned learner event; and
5. appends the outbox record.

A stale expected version fails closed. Reusing an idempotency key for a different
command fails closed. SQL/database failures never generate an empty replacement
state.

Replay reads the append-only event sequence in aggregate-version order. Versions
must be contiguous from zero. Replay returns the exact latest accepted state or
raises `ReplayDivergenceError`; it does not silently skip a gap or malformed event.

### Deterministic learning ownership

`LearningPlanService` remains unchanged as the deterministic decision core. It
still owns diagnosis, planning, evidence deltas, reviews, replanning, and assessment
calibration. Persistence wraps this service and may not introduce or modify a
learning decision.

### Full-stack compatibility path

The public product routes remain unchanged. In `postgres` mode they are served by a
compatibility orchestrator that:

- creates durable plans;
- resumes owned plans;
- imports a valid legacy signed token on first resume;
- verifies that mutation tokens equal the current stored snapshot;
- rejects stale tabs with HTTP 409;
- persists evidence, replanning, and assessment transitions; and
- preserves the existing React request and response contracts.

The Next.js same-origin proxy creates a random provider-neutral anonymous account
identifier in an `HttpOnly`, `SameSite=Lax` cookie, adds `Secure` on HTTPS, and
forwards account and per-command UUIDs only to FastAPI. Browser request bodies cannot
select an account identifier.

The signed token remains in browser local storage as a bounded projection and legacy
migration envelope. In `postgres` mode it is no longer authoritative.

## Verification implemented

- configuration validation and secret-confidentiality tests;
- persistence-contract invariant tests;
- complete in-memory durable create/resume/progress/replan/assessment cycle;
- automatic legacy-token import tests;
- safe HTTP mappings for not-found, conflict, unavailable storage, invalid learning
  requests, and invalid request context;
- real PostgreSQL commit/load/idempotency/outbox tests;
- real PostgreSQL replay and divergence tests;
- cross-account isolation tests;
- Alembic migration round-trip gate;
- Next.js proxy tests for new/reused/malformed cookies, HTTPS hardening, server-only
  account forwarding, per-command UUIDs, allowlisting, and preserved payloads;
- existing API, web, runtime-smoke, phase-gate, and gate-projection jobs retained.

API line and branch coverage remains required at 95% or higher. Exact-head acceptance
is not recorded until GitHub Actions executes all jobs successfully.

## Performance and resource boundaries

- no database engine or connection in `signed_state` mode;
- one lazy async engine per FastAPI application instance;
- `NullPool` prevents a serverless instance from retaining a private connection pool;
- one transaction and one snapshot/event/outbox write set per accepted mutation;
- indexed ownership lookup by account and learner;
- indexed append-only event lookup by learner;
- bounded learner-state, evidence-history, assessment-history, and request contracts;
- no blocking database calls on the event loop.

Latency and database-provider cost must be measured on the selected production
PostgreSQL service before activation. No unmeasured SLA or cost claim is made.

## Rollout and rollback

1. Keep production on `signed_state` while the branch is reviewed.
2. Provision PostgreSQL and inject the server-only database URL.
3. Run `alembic upgrade head` for the exact application revision.
4. Run confidentiality, migration, repository, web, and deployed end-to-end checks.
5. Enable `AI_PLATFORM_PERSISTENCE_MODE=postgres` only after all exact-head checks
   pass.
6. Roll back application traffic by returning to `signed_state`; retain database
   records for diagnosis and replay.

Normal rollback does not downgrade the production database. The downgrade exists for
migration testing and controlled pre-production reversal.

## Explicit remaining boundaries

P01 deliberately does not provide:

- managed OIDC, production login, account recovery, or cross-device identity;
- organization tenancy, employer/admin dashboards, or delegated authorization;
- personal-data deletion orchestration;
- an outbox delivery worker or external broker;
- object storage, artifact verification, LLM tutoring, payments, or notifications;
- market validation of the provisional role or assessment bank.

The anonymous cookie is a provider-neutral ownership bridge, not a substitute for
managed identity.

## Claim boundary

P01 establishes durable product infrastructure only. It does not satisfy V00, unlock
V01, validate the target role, certify mastery, or prove job readiness.
